# M03: ETL 转换

## 学习目标

- Shuffle 如何工作以及为什么它是 Spark 中最昂贵的操作
- 广播连接 vs 排序合并连接 — 何时使用每种
- 使用窗口函数进行去重
- 时间戳规范化和日期派生
- 数据质量指标输出

## 概述

这是 ETL 管道的核心。六个阶段将原始、已验证的事件转换为丰富的、聚合的分析数据集。

```
┌──────────────────────────────────────────────────────────────────┐
│                     ETL 转换 (M03)                                │
│                                                                  │
│  阶段 1: 规范化              阶段 4: 丰富（发布数据）             │
│  ┌──────────────────┐        ┌──────────────────────┐            │
│  │ 时间戳 → UTC     │        │ 排序合并连接         │            │
│  │ 派生 event_date  │        │ content_launch       │            │
│  │ year, month, day │        │ 键: content_id+region│            │
│  │ (窄操作——无      │        │ (SHUFFLE: 双方重新   │            │
│  │  Shuffle)        │        │  分布)               │            │
│  └────────┬─────────┘        └──────────┬───────────┘            │
│           │                             │                         │
│  阶段 2: 去重                阶段 5: 派生                         │
│  ┌──────────────────┐        ┌──────────────────────┐            │
│  │ row_number() OVER │       │ launch_delay_days     │            │
│  │ PARTITION BY      │       │ watch_hours           │            │
│  │ event_id ORDER BY │       │ is_completed 标志     │            │
│  │ timestamp DESC    │       │ (窄操作——无 Shuffle)  │            │
│  │ (SHUFFLE: 窗口    │       └──────────┬───────────┘            │
│  │  重新分布)        │                  │                         │
│  └────────┬─────────┘                  │                         │
│           │                             │                         │
│  阶段 3: 丰富（元数据）      阶段 6: 聚合                         │
│  ┌──────────────────┐        ┌──────────────────────┐            │
│  │ 广播连接          │       │ GROUP BY content_id,  │            │
│  │ content_metadata  │       │ region, device_type,  │            │
│  │ (1K 行 → 适合     │       │ event_date            │            │
│  │  内存)            │       │ (SHUFFLE: GROUP BY   │            │
│  │ (无 Shuffle!)     │       │  重新分布)            │            │
│  └──────────────────┘        └──────────────────────┘            │
└──────────────────────────────────────────────────────────────────┘
```

## 核心概念

### 1. Shuffle — 最昂贵的操作

**Shuffle** 发生在 Spark 必须在分区之间重新分布数据时。每个分区的数据被发送到其他每个分区——这意味着网络 I/O、磁盘 I/O 和序列化。

```
Shuffle 前:                  Shuffle 后 (按键):
分区 0: [A, B, C]           分区 0: [A, A, A]
分区 1: [A, D, E]  →        分区 1: [B, B]
分区 2: [B, C, A]           分区 2: [C, C, D, E]
```

在本模块中，Shuffle 发生在：
- **去重**：`PARTITION BY event_id` — 相同 event_id 的所有行必须在同一分区
- **排序合并连接**：双方按连接键重新分布
- **聚合**：`GROUP BY` 按分组列重新分布

### 2. 广播连接 — 避免 Shuffle

当一个表足够小可以放入执行器内存（< 10 MB）时，Spark 可以将其**广播**到每个执行器，而不是重新分布：

```
广播连接:                        排序合并连接:
┌──────┐  ┌──────┐              ┌──────┐    ┌──────┐
│ 大表 │  │ 小表 │              │ 大表 │    │ 小表 │
│      │  │(1K)  │              │      │    │      │
└──┬───┘  └──┬───┘              └──┬───┘    └──┬───┘
   │         │                     │           │
   │    ┌────▼────┐                ▼           ▼
   │    │  广播   │            ┌─────────────────┐
   │    │到所有   │            │    SHUFFLE      │
   │    │执行器   │            │ 按连接键重新分布 │
   │    └────┬────┘            └────────┬────────┘
   ▼         ▼                         ▼
┌─────────────────┐            ┌─────────────────┐
│  每个执行器上   │            │  每个执行器上   │
│  本地连接       │            │  排序 + 合并    │
│  (无 Shuffle)   │            │                 │
└─────────────────┘            └─────────────────┘
```

在我们的管道中：`content_metadata`（1,000 行，~0.1 MB）→ 完美的广播候选。

### 3. 窗口函数去重

```sql
row_number() OVER (PARTITION BY event_id ORDER BY event_timestamp DESC)
```

这为每个 event_id 的最新事件分配行号 1。我们保留行 1（最新），将行 > 1（较旧的重复）发送到拒绝队列。

### 4. 数据质量指标

每个阶段都会输出指标。这些是规范中的"可观测性"要求——你始终知道数据发生了什么。

## 常见陷阱

- **默认 Shuffle 分区数 = 200**：对于小数据（10K 行），这会创建 200 个微小任务。Spark 的 AQE（自适应查询执行）可以合并它们，但仍会带来开销。
- **广播阈值**：默认 10 MB。如果"小"表超过此值，Spark 会静默回退到排序合并连接。在物理计划中注意这一点。
- **不带 PARTITION BY 的窗口函数**：将所有内容放入一个分区——适用于全局排序，但对并行性不利。
