# M06: 增量 ETL 与可靠性

## 学习目标

- 如何仅处理新数据而非全表扫描
- 设计幂等管道：重新运行产生相同输出
- 迟到数据处理：滚动重新处理窗口
- 历史数据回填策略
- Schema 演化策略

## 概述

一次性批处理作业很容易。每天运行而不损坏数据的生产管道很难。本模块涵盖了使 ETL 可靠所需的模式。

## 核心概念

### 1. 幂等性

如果一个操作运行一次的效果与运行 N 次相同，则该操作是**幂等**的。

**我们的策略**：分区级覆写。处理 `event_date=2026-08-12` 时，使用 `mode("overwrite")` 写入。如果输入数据未更改，输出完全一致。

**破坏幂等性的因素**：
- `mode("append")` — 重新运行时重复行
- 非确定性转换（如在派生逻辑中使用 `current_timestamp()`）
- 从两次运行之间发生变化的源读取

### 2. 迟到数据

事件并不总是准时到达。用户的设备可能处于离线状态，或者批量上传可能延迟。

**迟到窗口**：D-2 到 D。每次运行时重新处理最近 3 天的数据，而不仅仅是今天。

窗口大小是权衡：更大 = 捕获更多迟到事件但计算成本更高。

### 3. 回填

回填处理历史日期范围——适用于：
- 初始加载：处理一年的历史数据
- Bug 修复：重新处理受代码更改影响的日期
- Schema 演化：以新格式重写旧分区

### 4. 分区检测

不进行全表扫描，而是比较目录列表。这是 O(n) 的分区数复杂度，而非 O(n) 的行数复杂度。
